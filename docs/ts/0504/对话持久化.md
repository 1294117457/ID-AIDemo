# AI 对话持久化设计文档

> 需求：新增压缩会话功能，用户可以新开启对话，同时旧对话数据不丢失，后续可以重新选择对话继续。
>
> 范围：仅针对 `idfrontend/src/views/ai-agent`（AI 助手悬浮球聊天），不涉及 `idfrontend/src/views/score/index.vue`（加分申请流程）。

---

## 一、设计原则

**核心原则：会话数据全部聚合到 idagent 的 SQLite 中，idbackend 退化为透明代理。**

| 原则 | 说明 |
|------|------|
| **单一数据源** | idagent 独自管理所有会话数据（消息 + 元数据 + LangGraph Checkpoint），不引入额外的 MySQL 依赖 |
| **后端零感知** | idbackend 只需注入 `x-user-id` 请求头，不存储、不查询任何会话业务数据 |
| **自包含性** | idagent 独立部署，对外只暴露 HTTP API，SQLite 文件自持 |
| **复用现有 Checkpoint** | LangGraph 的 SQLite Checkpoint (`data/checkpoints.db`) 继续用于状态恢复，不废弃 |

---

## 二、现有架构分析

### 2.1 当前数据存储情况

| 存储位置 | 文件 | 内容 | 管理方 |
|----------|------|------|--------|
| idagent SQLite | `data/agent.db` | AI 配置 (`ai_config` 表) | idagent |
| idagent SQLite | `data/checkpoints.db` | LangGraph Checkpoint | idagent (langgraph-checkpoint-sqlite) |
| MySQL | `iddata` 数据库 | 用户、申请、文件等业务数据 | idbackend |
| 前端内存 | `messages ref` | 当前对话消息 | idfrontend (页面刷新即丢失) |

### 2.2 当前对话流程（改造前）

```
前端：sessionId = "sess_" + Date.now()（纯前端生成，刷新即丢）
     messages = ref([])  （纯内存，刷新即丢）

后端：/api/agent/stream → 转发 FormData → idagent

idagent：thread_id = sessionId
       LangGraph Checkpoint 持久化（依赖 sessionId）
       压缩在 memory.ts 中自动触发（12条消息）
```

### 2.3 核心痛点

| 问题 | 说明 |
|------|------|
| 前端无会话持久化 | 页面刷新后所有消息消失 |
| 无历史会话列表 | 用户无法查看/选择过去的对话 |
| sessionId 纯前端生成 | 新建对话时旧 sessionId 丢失，Checkpoint 无法关联 |
| 无会话标题/元数据 | Checkpoint 仅存结构化状态，无用户可见的标题和时间 |
| 耦合 MySQL 不可行 | 为 AI 对话单独在 MySQL 建表增加运维复杂度 |

### 3.2 双数据源职责划分

| 数据源 | 内容 | 用途 | 写入时机 |
|--------|------|------|----------|
| `ai_message` (SQLite) | 用户消息 + AI 回复的纯文本 | 前端 UI 渲染、消息列表展示 | 实时写入 |
| `checkpoints.db` (LangGraph) | LangGraph 内部完整状态 | 恢复对话意图、documentText、压缩上下文等结构化数据 | LangGraph 自动管理 |
| `ai_conversation` (SQLite) | 会话标题、时间、用户关联 | 会话列表 UI、归档管理 | 新建/更新标题时写入 |

**关键**：前端消息 UI 从 `ai_message` 渲染，LangGraph 状态从 `checkpoints.db` 恢复，二者通过 `sessionId` 关联。

## 四、数据库设计（idagent SQLite）

### 4.1 改造 `data/agent.db` Schema

在 `initDb()` 中追加建表语句，新增两张表：

#### `ai_conversation` — 会话元数据表

```sql
CREATE TABLE IF NOT EXISTS ai_conversation (
  id          INTEGER PRIMARY KEY AUTOINCREMENT,
  user_id     TEXT    NOT NULL,
  session_id  TEXT    NOT NULL UNIQUE,
  title       TEXT    NOT NULL DEFAULT '新对话',
  status      INTEGER NOT NULL DEFAULT 1,          -- 1=进行中 0=归档
  is_deleted  INTEGER NOT NULL DEFAULT 0,           -- 软删除标记
  created_at  TEXT    NOT NULL,                    -- ISO 8601 时间字符串
  updated_at  TEXT    NOT NULL
);

CREATE INDEX IF NOT EXISTS idx_conv_user     ON ai_conversation(user_id);
CREATE INDEX IF NOT EXISTS idx_conv_session ON ai_conversation(session_id);
```

> `user_id` 格式为 `"type:id"`（如 `"student:123"` 或 `"admin:456"`），由 idbackend 从 Token 解析后通过 `x-user-id` 请求头传入。idagent 不解析 Token，只存储和按 `user_id` 过滤。

#### `ai_message` — 消息表

```sql
CREATE TABLE IF NOT EXISTS ai_message (
  id          INTEGER PRIMARY KEY AUTOINCREMENT,
  session_id  TEXT    NOT NULL,
  role        TEXT    NOT NULL,          -- user / assistant / interrupt
  content     TEXT    NOT NULL,
  msg_type    TEXT    NOT NULL DEFAULT 'message',   -- message / interrupt / error
  extra_data  TEXT,                       -- JSON 字符串（suggestions 等）
  created_at  TEXT    NOT NULL            -- ISO 8601 时间字符串
);

CREATE INDEX IF NOT EXISTS idx_msg_session ON ai_message(session_id);
CREATE INDEX IF NOT EXISTS idx_msg_created ON ai_message(created_at);
```

### 4.2 与现有表的关系

```
agent.db
├── ai_config         ← 已有（AI 配置）
├── ai_conversation   ← 新增（会话元数据）
└── ai_message        ← 新增（消息记录）

checkpoints.db
└── (langgraph-checkpoint-sqlite 自动管理的表)
    └── thread_id = session_id（由 ai_conversation.session_id 关联）
```

```typescript
// src/6service/ConversationService.ts
import { getDb } from '../1config/config.js'

export interface ConversationMeta {
  id: number
  userId: string
  sessionId: string
  title: string
  status: number
  createdAt: string
  updatedAt: string
  messageCount: number
  lastMessage: string  // 最后一条消息预览（截断50字）
}

export interface MessageRecord {
  id: number
  sessionId: string
  role: string
  content: string
  msgType: string
  extraData: any
  createdAt: string
}

// ── 会话元数据操作 ──────────────────────────────────────────────────

export function createConversation(userId: string, firstMessage: string): { id: number; sessionId: string; title: string } {
  const db = getDb()
  const sessionId = `sess_${crypto.randomUUID().replace(/-/g, '')}`
  const title = firstMessage.slice(0, 30) || '新对话'
  const now = new Date().toISOString()

  const result = db.prepare(`
    INSERT INTO ai_conversation (user_id, session_id, title, status, is_deleted, created_at, updated_at)
    VALUES (?, ?, ?, 1, 0, ?, ?)
  `).run(userId, sessionId, title, now, now)

  return { id: result.lastInsertRowid as number, sessionId, title }
}

export function getConversations(userId: string, limit = 50, offset = 0): ConversationMeta[] {
  const db = getDb()

  return db.prepare(`
    SELECT
      c.id, c.user_id, c.session_id, c.title, c.status, c.created_at, c.updated_at,
      COUNT(m.id)  AS message_count,
      MAX(m.content) AS last_message
    FROM ai_conversation c
    LEFT JOIN ai_message m ON m.session_id = c.session_id
    WHERE c.user_id = ? AND c.is_deleted = 0
    GROUP BY c.id
    ORDER BY c.updated_at DESC
    LIMIT ? OFFSET ?
  `).all(userId, limit, offset) as ConversationMeta[]
}

export function getConversationBySession(sessionId: string): ConversationMeta | null {
  const db = getDb()
  const row = db.prepare(`
    SELECT c.*, COUNT(m.id) AS message_count, MAX(m.content) AS last_message
    FROM ai_conversation c
    LEFT JOIN ai_message m ON m.session_id = c.session_id
    WHERE c.session_id = ? AND c.is_deleted = 0
    GROUP BY c.id
  `).get(sessionId) as ConversationMeta | undefined
  return row ?? null
}

export function updateConversationTitle(sessionId: string, title: string): void {
  const db = getDb()
  db.prepare(`
    UPDATE ai_conversation SET title = ?, updated_at = ? WHERE session_id = ?
  `).run(title, new Date().toISOString(), sessionId)
}

export function archiveConversation(sessionId: string): void {
  const db = getDb()
  db.prepare(`
    UPDATE ai_conversation SET status = 0, updated_at = ? WHERE session_id = ?
  `).run(new Date().toISOString(), sessionId)
}

export function deleteConversation(sessionId: string): void {
  const db = getDb()
  const tx = db.transaction(() => {
    db.prepare(`UPDATE ai_conversation SET is_deleted = 1 WHERE session_id = ?`).run(sessionId)
    db.prepare(`DELETE FROM ai_message WHERE session_id = ?`).run(sessionId)
  })
  tx()
}

export function searchConversations(userId: string, keyword: string): ConversationMeta[] {
  const db = getDb()
  return db.prepare(`
    SELECT c.id, c.user_id, c.session_id, c.title, c.status, c.created_at, c.updated_at,
           COUNT(m.id) AS message_count, MAX(m.content) AS last_message
    FROM ai_conversation c
    LEFT JOIN ai_message m ON m.session_id = c.session_id
    WHERE c.user_id = ? AND c.is_deleted = 0
      AND (c.title LIKE ? OR m.content LIKE ?)
    GROUP BY c.id
    ORDER BY c.updated_at DESC
    LIMIT 50
  `).all(userId, `%${keyword}%`, `%${keyword}%`) as ConversationMeta[]
}

// ── 消息操作 ──────────────────────────────────────────────────────

export function appendMessage(sessionId: string, role: string, content: string, msgType = 'message', extraData?: any): number {
  const db = getDb()
  const now = new Date().toISOString()
  const result = db.prepare(`
    INSERT INTO ai_message (session_id, role, content, msg_type, extra_data, created_at)
    VALUES (?, ?, ?, ?, ?, ?)
  `).run(sessionId, role, content, msgType, extraData ? JSON.stringify(extraData) : null, now)

  // 更新会话的 updated_at
  db.prepare(`UPDATE ai_conversation SET updated_at = ? WHERE session_id = ?`).run(now, sessionId)
  return result.lastInsertRowid as number
}

export function getMessages(sessionId: string): MessageRecord[] {
  const db = getDb()
  return db.prepare(`
    SELECT id, session_id, role, content, msg_type, extra_data, created_at
    FROM ai_message
    WHERE session_id = ?
    ORDER BY created_at ASC
  `).all(sessionId) as MessageRecord[]
}

export function getLastMessage(sessionId: string): MessageRecord | null {
  const db = getDb()
  const row = db.prepare(`
    SELECT id, session_id, role, content, msg_type, extra_data, created_at
    FROM ai_message
    WHERE session_id = ?
    ORDER BY created_at DESC
    LIMIT 1
  `).get(sessionId) as MessageRecord | undefined
  return row ?? null
}
```

```typescript
// ── 发送消息时：追加用户消息到 SQLite ────────────────────────────────

export async function* streamAgent(input: AgentInput): AsyncGenerator<{ type: string; data: any }> {
  const config = { configurable: { thread_id: input.sessionId } }
  const app = await getApp()

  // 追加用户消息到 SQLite（若提供 userId）
  if (input.userId) {
    appendMessage(input.sessionId, 'user', input.userInput)
  }

  // ... 压缩逻辑 ...

  // SSE 流式推送 + 累积 AI 回复
  let assistantContent = ''
  for await (const event of app.streamEvents(...)) {
    // ... token yield ...
    if (event.event === 'on_chat_model_stream') {
      const token = event.data?.chunk?.content
      if (token) {
        assistantContent += token
        yield { type: 'token', data: { content: token } }
      }
    }
  }

  // SSE 结束后，将 AI 回复写入 SQLite
  if (input.userId && assistantContent) {
    appendMessage(input.sessionId, 'assistant', assistantContent)
  }

  // ... interrupt / result yield ...
}
```

## 六、idbackend 端改造（透明代理）

### 6.1 改造原则

idbackend **不做任何会话业务逻辑**，只做三件事：

1. **鉴权**：验证请求携带的 Token
2. **注入**：从 Token 中解析 `userId`，附加到 `x-user-id` 请求头
3. **透传**：将请求原封不动转发到 idagent

### 6.2 新增 Controller

```java
// AiConversationProxyController.java

@RestController
@RequestMapping("/api/ai/conversation")
public class AiConversationProxyController {

    @Autowired
    private RestTemplate restTemplate;

    @Value("${ai-agent.base-url}")
    private String idagentBaseUrl;

    // GET /api/ai/conversation/list
    @GetMapping("/list")
    public ResponseEntity<byte[]> listConversations(
            HttpServletRequest req,
            @RequestParam(defaultValue = "50") Integer limit,
            @RequestParam(defaultValue = "0") Integer offset) {

        String userId = extractUserId(req);  // 从 JWT Token 解析
        String targetUrl = idagentBaseUrl + "/ai/conversation/list"
                + "?limit=" + limit + "&offset=" + offset;

        return forwardWithUserId(req, userId, targetUrl);
    }

    // GET /api/ai/conversation/{sessionId}/messages
    @GetMapping("/{sessionId}/messages")
    public ResponseEntity<byte[]> getMessages(
            HttpServletRequest req,
            @PathVariable String sessionId) {

        String userId = extractUserId(req);
        String targetUrl = idagentBaseUrl + "/ai/conversation/" + sessionId + "/messages";
        return forwardWithUserId(req, userId, targetUrl);
    }

    // POST /api/ai/conversation/create
    @PostMapping("/create")
    public ResponseEntity<byte[]> createConversation(
            HttpServletRequest req,
            @RequestBody Map<String, String> body) {

        String userId = extractUserId(req);
        String targetUrl = idagentBaseUrl + "/ai/conversation/create";
        return forwardPostWithUserId(req, userId, targetUrl, body);
    }

    // DELETE /api/ai/conversation/{sessionId}
    @DeleteMapping("/{sessionId}")
    public ResponseEntity<byte[]> deleteConversation(
            HttpServletRequest req,
            @PathVariable String sessionId) {

        String userId = extractUserId(req);
        String targetUrl = idagentBaseUrl + "/ai/conversation/" + sessionId;
        return forwardDeleteWithUserId(req, userId, targetUrl);
    }

    // PUT /api/ai/conversation/{sessionId}/title
    @PutMapping("/{sessionId}/title")
    public ResponseEntity<byte[]> updateTitle(
            HttpServletRequest req,
            @PathVariable String sessionId,
            @RequestBody Map<String, String> body) {

        String userId = extractUserId(req);
        String targetUrl = idagentBaseUrl + "/ai/conversation/" + sessionId + "/title";
        return forwardPutWithUserId(req, userId, targetUrl, body);
    }

    // ── 内部方法 ──────────────────────────────────────────────────

    private String extractUserId(HttpServletRequest req) {
        String token = req.getHeader("Authorization").replace("Bearer ", "");
        // 调用 JWT 解析工具，提取 userId
        return jwtUtil.extractUserId(token);
    }

    private <T> ResponseEntity<byte[]> forwardWithUserId(
            HttpServletRequest req, String userId, String targetUrl) {
        HttpHeaders headers = new HttpHeaders();
        headers.add("x-user-id", userId);
        // ... 复制其他必要 headers ...
        HttpEntity<Void> entity = new HttpEntity<>(headers);
        return restTemplate.exchange(targetUrl, HttpMethod.GET, entity, byte[].class);
    }
}
```

```typescript
  isLoadingHistory.value = true

    // 从 SQLite 加载消息列表
    const msgs = await getMessagesApi(conv.sessionId)

  }

}
```

## 九、idagent Checkpoint 与 SQLite 消息双写策略

### 9.1 职责划分

| 数据源 | 内容 | 作用 | 谁写入 |
|--------|------|------|--------|
| `ai_message` | 消息纯文本 | 前端 UI 渲染 | `streamAgent()` 中实时写入 |
| `checkpoints.db` | LangGraph 完整状态 | 状态恢复、意图保持 | LangGraph 自动管理 |
| `ai_conversation` | 元数据 | 会话列表展示 | `createConversation()` 等显式写入 |

### 9.2 一致性保证

- **用户消息**：先写入 SQLite（`appendMessage`），再发送 LangGraph，保证消息不丢
- **AI 回复**：流式 SSE 给前端的同时累积，结束后写入 SQLite；若中途断开，Checkpoint 中已有记录，下次恢复时从 Checkpoint 读取完整状态
- **删除操作**：在 `deleteConversation()` 事务中同时删除 `ai_message` 记录和 Checkpoint

## 十一、风险与注意事项

### 11.1 数据一致性

| 风险 | 缓解方案 |
|------|----------|
| SSE 中途断开，AI 回复未写入 `ai_message` | Checkpoint 中有完整消息，下一次对话时从 Checkpoint 恢复 |
| `ai_message` 和 Checkpoint 内容不一致 | Checkpoint 是真实数据源，`ai_message` 丢失可通过 Checkpoint 重建 |
| 事务失败（`ai_message` 写成功但 Checkpoint 失败） | Checkpoint 失败不影响主流程；可在恢复时从 `ai_message` 补全 |

### 11.2 SQLite 性能

| 场景 | 风险 | 缓解 |
|------|------|------|
| 大量用户、长时间会话 | `ai_message` 表行数快速增长 | `session_id` 索引 + 分页查询；历史会话归档到 `status=0` |
| 多实例部署（将来扩展） | SQLite 不支持跨进程共享 | 当前 idagent 为单实例，暂无此问题；扩展时切换到 PostgreSQL |

### 11.3 安全

- `user_id` 隔离：所有查询强制带 `WHERE user_id = ?`，idbackend 负责验证 Token 并注入 `x-user-id`
- 软删除：`is_deleted` 标记防误删，数据不物理删除
- 管理员视图（可选扩展）：admin 面板传递特殊 `x-user-id` 格式（如 `admin:all`），idagent 可据此做权限区分

## 十二、方案对比

| 对比项 | MySQL 方案 | **SQLite 聚合方案（本文）** |
|--------|-----------|--------------------------|
| 数据源数量 | 2（MySQL + idagent SQLite） | **1（仅 idagent SQLite）** |
| 后端改动 | 中（新建表、Service、Controller） | **小（退化为透明代理）** |
| 运维复杂度 | 高（MySQL + idagent 双重维护） | **低（仅 idagent 自包含）** |
| 跨服务一致性 | 需处理分布式事务 | **无此问题** |
| 自包含性 | 低（依赖外部 MySQL） | **高（完全自包含）** |
| 数据查询能力 | 强（复杂 SQL、跨表 JOIN） | 弱（SQLite 功能有限，但够用） |
| 部署简单性 | 需额外部署 MySQL | **随 idagent 一起部署** |
