## 一、背景与目标

### 1.1 当前结构概况

```
src/
├── 1config/           配置层（DB + AI 配置）
├── 1common/           公共基础设施（类型、常量、提示词、工具）
├── 2model/            LLM 工厂
├── 3state/            LangGraph 状态定义
├── 4node/             图节点（classify / consult / apply 子图）
├── 5graph/            图编排
├── 6service/          业务编排
├── 7controller/        HTTP 适配层
├── 7mcp/              后端工具调用
└── 8rag/              向量知识库
```

### 1.2 本次优化目标

1. **合并 `1config/` + `1common/`** → 统一为单一 `1common/` 目录
2. **重新规划目录编号体系**，消除编号跳跃（4→5→6→7→7mcp→8）和层级归属混乱
3. **提升可读性和可维护性**，从功能性、架构、可读性三个维度全面优化

## 二、`1config/` + `1common/` 合并方案

### 2.1 合并理由

| 目录 | 职责 | 合并合理性 |
|---|---|---|
| `1config/` | 环境变量、DB 初始化、AI 配置读写 | 本质上也是"公共基础设施"，与 `1common/` 定位重叠 |
| `1common/` | 共享类型、常量、提示词、工具函数 | 天然适合承载 `config` 的导出 |

合并后，`1common/` 成为项目中**唯一一个公共基础设施层**，职责清晰，引用路径统一。

### 2.2 合并后目标结构

```
src/1common/
├── config.ts           ← 移动 src/1config/config.ts → src/1common/config.ts
├── constants.ts        保持（节点名、SKIP_NODES、压缩阈值）
├── prompts.ts          保持（所有 LLM 提示词模板）
├── types/
│   └── shared.ts       保持（全部跨层共享类型）
└── utils/
    └── index.ts        保持（文件解码、目录、API 响应工具）
```

### 2.3 引用影响范围

以下文件中的 `../1config/config.js` 引用需要改为 `../1common/config.js`：

| 文件 | 修改内容 |
|---|---|

| `5graph/graph.ts` | `from '../1config/config.js'` → `'../1common/config.js'` |
| `6service/AgentService.ts` | `from '../1config/config.js'` → `'../1common/config.js'` |
| `6service/ConversationService.ts` | `` |
| `7controller/config/index.ts` | `from '../../1config/config.js'` → `'../../1common/config.js'` |
| `4node/consult/nodes/answerNode.ts` | `from '../../../1config/config.js'` → `'../../../1common/config.js'` |
| `7mcp/mcpClient.ts` | `from '../1config/config.js'` → `'../1common/config.js'` |

## 三、目录编号体系重规划

### 3.1 当前问题

| 问题 | 说明 |
|---|---|
| **编号跳跃** | 4 → 5 → 6 → 7 → 7mcp → 8，编号不连续，逻辑层级不清晰 |
| **层级归属混乱** | `7mcp` 和 `8rag` 实际上都是服务支撑层，但编号与 `7controller` 平级 |
| **层级顺序不直观** | `5graph` 在 `4node` 后面，实际 graph 依赖 node，编号应反直觉 |
| **4node 层归属模糊** | 节点到底是图编排层的一部分还是独立层？`5graph` 引用 `4node/*` 说明 graph > node，但编号反之 |

### 3.2 重规划方案（保持现有文件，仅改编号）

**原则：按依赖方向编号（底层 → 上层），编号小的层不依赖编号大的层。**

```
src/
├── 1common/            公共基础设施层（config + types + utils + constants + prompts）
├── 2state/             LangGraph 状态定义层（State Schema）
├── 3node/              图节点层（所有节点：classify / consult / apply / memory）
├── 4graph/             图编排层（LangGraph 组装 + Checkpoint）
├── 5service/           业务编排层（Agent / Knowledge / Conversation 服务）
├── 6rag/               向量知识库层（RAG 管道：loader / store / 业务编排）
├── 7mcp/               后端工具调用层（HTTP → idbackend）
└── 8controller/        HTTP 适配层（路由 + 请求处理）
```

### 3.3 变更对照表

| 原路径 | 新路径 | 说明 |
|---|---|---|
| `src/1config/` | `src/1common/` | 合并，config.ts 移入 |
| `src/1common/` | `src/1common/` | 合并后保留 |
| `src/2model/` | `src/2model/` | **不变**（独立为工具层，不参与主依赖链）|
| `src/3state/` | `src/2state/` | 编号调整 |
| `src/4node/` | `src/3node/` | 编号调整 |
| `src/5graph/` | `src/4graph/` | 编号调整 |
| `src/6service/` | `src/5service/` | 编号调整 |
| `src/8rag/` | `src/6rag/` | 编号调整，数字顺接 |
| `src/7mcp/` | `src/7mcp/` | **不变**（已顺接）|
| `src/7controller/` | `src/8controller/` | 编号调整 |

**重命名后引用链**（严格单向依赖，无环）：
```
1common ← 2state ← 3node ← 4graph ← 5service ← 8controller
              ↑                              ↑
         2model（独立）              6rag / 7mcp（支撑层）
```

## 四、功能性与架构优化

### 4.1 架构层面优化建议

#### 建议一：将 `6service/memory.ts` 移入 `6service/` 目录（已是现状，保持即可）

**现状**：`memory.ts` 已在 `6service/` 下，不在 `4node/` 中，职责正确。

---

#### 建议二：提取 `AgentService.ts` 中的配置注入逻辑

**现状**：`AgentService.ts` 直接在函数参数中解析 `Authorization` header 和 `x-user-id`，逻辑分散在 `parseAgentParams` 和 `streamResume` 中两处重复。

**建议**：新增 `src/5service/utils/auth.ts`，统一从 Express Request 提取认证信息：

```typescript
// src/5service/utils/auth.ts（新增）
import type { Request } from 'express'

export interface AuthContext {
  userId:    string | null
  userToken: string
}

export function extractAuth(req: Request): AuthContext {
  const userId    = (req.headers['x-user-id'] as string) || null
  const auth      = (req.headers['authorization'] as string) || ''
  const userToken = auth.startsWith('Bearer ') ? auth.slice(7) : auth
  return { userId, userToken }
}
```

**涉及修改**：`AgentService.ts` 的 `parseAgentParams` 和 `streamResume` 引用此函数。

---

#### 建议三：`ConversationService.ts` 抽取类型定义

**现状**：`ConversationService.ts` 中接口定义（如 `Conversation`, `Message` 等）与业务逻辑混在一起。

**建议**：移动到 `1common/types/` 下，保持类型与逻辑分离。

---

#### 建议四：统一 MCP 工具的错误处理

**现状**：`mcpClient.ts` 中三个 MCP 工具各自独立，错误处理逻辑分散。

**建议**：在 `1common/` 新增 `1common/errors.ts`，定义统一的 MCP 错误类型，并在 `mcpClient.ts` 中集中处理。

---

### 4.2 功能层面优化建议

#### 建议五：`consult` 子图复用 `analyzeMatchNode` 的 MCP 模板拉取（可选扩展）

**现状**：`consult` 子图仅做 RAG 检索，不拉取 templates。已有设计是合理的（咨询场景不需要加分模板）。

**建议**：保持现状，此项可作为未来扩展点记录，不强制修改。

---

#### 建议六：`analyzeMatchNode` 缓存 templates（可选性能优化）

**现状**：每次进入 `apply` 子图都会通过 MCP 重新拉取 `templates`，高并发场景会产生大量重复请求。

**建议**：在 `5service/AgentService.ts` 层添加可选的 templates 缓存（如 5 分钟 TTL），对同一用户会话复用 templates。

---

#### 建议七：支持 `analyzeCertificate` 从后端自动拉取 templates

**现状**：`analyze/certificate` 接口要求前端传递 `templates` JSON 字符串，如果未传则为空数组。

**建议**：当 `templates` 未传时，自动调用 `getScoreTemplatesMcp` 从后端拉取（需要 `userToken`，可从请求 header 获取），无需前端手动传。

---

#### 建议八：清理未使用的配置项

**现状**：`.env` 中 `BACKEND_URL` 使用的是 `JAVA_BACKEND_URL` 环境变量，而配置项是 `JAVA_BACKEND_URL ?? 'http://localhost:8080'`，但实际生产环境 idbackend 可能是另一个地址。

**建议**：统一环境变量命名规范，在 `1common/config.ts` 中添加注释说明各 URL 的用途。

---

### 4.3 可读性优化建议

#### 建议九：为所有 State 类型添加 JSDoc 注释

**现状**：`MainState.ts` 等文件有注释，但接口参数、返回值的说明分散。

**建议**：在 `1common/types/shared.ts` 中的 `AgentInput`、`AgentResult` 等核心类型上增加 JSDoc，说明每个字段的来源和用途。

---

#### 建议十：统一导出模式（barrel 文件规范）

**现状**：部分目录有 `index.ts` 导出，部分没有（如 `2model/`、`6service/service.ts` 是兼容层）。

**建议**：所有层目录都应有 `index.ts`，形成明确的公共 API 边界：

```
src/5service/
├── index.ts      统一导出 AgentService + KnowledgeService + ConversationService 的公开 API
├── AgentService.ts
├── KnowledgeService.ts
├── ConversationService.ts
└── utils/
    └── auth.ts  （新增）认证上下文提取
```

---

#### 建议十一：`SKIP_NODES` 动态化

**现状**：`SKIP_NODES` 是一个硬编码的 `Set`，节点名变化时需要同步修改两处（`constants.ts` 和 `graph.ts` 中的 `GRAPH_NODE_NAMES`）。

**建议**：`SKIP_NODES` 应基于 `GRAPH_NODE_NAMES` 动态计算，而非手动维护两份列表：

```typescript
// constants.ts
export const GRAPH_NODE_NAMES = { ... } as const

// SKIP_NODES 不再手动列举，而是基于 GRAPH_NODE_NAMES 过滤
export const SKIP_NODES = new Set([
  GRAPH_NODE_NAMES.CLASSIFY,
  GRAPH_NODE_NAMES.ASK,
  GRAPH_NODE_NAMES.RETRIEVE,
  GRAPH_NODE_NAMES.FETCH_POLICY,
  GRAPH_NODE_NAMES.ANALYZE_AND_MATCH,
  GRAPH_NODE_NAMES.SUMMARIZE,
])
// 此写法已经是动态引用（只要 GRAPH_NODE_NAMES 更新，SKIP_NODES 自动同步）
```

**现状检查**：经代码审查，当前 `constants.ts` 已采用上述写法，无需修改 ✅。

---

#### 建议十二：统一状态类型命名规范

**现状**：`MainStateType`、`ApplyStateType`、`ConsultStateType` 三个类型都有 `Type` 后缀，但 `ScoreTemplate` 等其他类型无后缀。

**建议**：统一去掉所有类型别名后缀 `Type`，直接用 `MainState`、`ApplyState`、`ConsultState`（去掉别名，直接 export 推导类型）：

```typescript
// 现状
export type MainStateType = typeof MainState.State
export type ApplyStateType = typeof ApplyState.State

// 建议
export type MainState    = typeof MainState.State
export type ApplyState   = typeof ApplyState.State
```

**影响文件**：所有引用这些类型的文件（`classifyNode.ts`、`answerNode.ts`、`analyzeMatchNode.ts` 等），需要同步去掉 `Type` 后缀。

## 六、优化优先级与实施计划

### Phase 1：合并 1config + 1common（低风险，高价值）

**目标**：消除职责重叠，简化引用路径

**涉及文件**：仅 `1common/` 和 `1config/` 的文件操作 + 7 个引用路径更新

**预估工时**：约 15 分钟

**风险**：低（仅移动文件和更新 import 路径）

---

### Phase 2：目录编号重规划（中风险，架构价值高）

**目标**：消除编号跳跃，建立清晰的单向依赖链

**涉及操作**：重命名 7 个目录 + 更新所有引用路径

**预估工时**：约 40 分钟

**风险**：中等（目录重命名量大，需完整测试验证）

---

### Phase 3：功能与可读性优化（可分期进行）

**目标**：提升代码质量、可维护性和功能健壮性

| 优化项 | 优先级 | 工时 |
|---|---|---|
| 提取 AuthContext 工具 | 高 | 15 分钟 |
| analyzeCertificate 自动拉取 templates | 高 | 15 分钟 |
| State 类型命名规范（去 Type 后缀） | 中 | 20 分钟 |
| MCP 错误类型集中管理 | 中 | 20 分钟 |
| templates 缓存（可选性能优化） | 低 | 30 分钟 |
