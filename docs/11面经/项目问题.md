问题二：对话存储与上下文处理确实需要优化
看你的代码，有几个明显的问题：

问题 2.1：summarize 节点存在但从未被触发

summarize 节点被定义在 SKIP_NODES 里，说明你原本想用它做摘要压缩。但实际流程里从来没触发过——当上下文超限时，直接拒绝了：

这意味着：对话到 20 条消息后，Agent 就"死"了，用户只能开新会话，历史全部丢失。

问题 2.2：State 中 messages 无限累积
export const MainState = Annotation.Root({
  ...MessagesAnnotation.spec,
  // ...
})
messages 用的是默认的 MessagesAnnotation.spec，这意味着每轮对话消息都会追加进去，没有上限、没有摘要、没有滑动窗口。

优化方案（面试可讲的）
方案一：上下文摘要压缩（最实用）
触发时机：messages 数量达到阈值（比如 15 条）时
压缩方式：
  1. 把前 N 条消息交给 LLM 做摘要
  2. 保留最近 5 轮完整对话（保留细节）
  3. 将摘要 + 最近对话 合并为新的 messages
  4. 继续往后追加
代码改动只需要在 service.ts 里加一个判断：

async function compressContext(config) {
  const snapshot = await app.getState(config)
  const msgs = snapshot.values.messages
  if (msgs.length < 15) return false
  
  const recentMsgs = msgs.slice(-10) // 保留最近 10 条
  const olderMsgs = msgs.slice(0, -10)
  
  // 用 LLM 摘要 olderMsgs
  const summary = await summarizeMessages(olderMsgs)
  // 更新 checkpoint，把摘要注入回去
  await app.updateState(config, {
    messages: [new SystemMessage(`【对话摘要】${summary}`), ...recentMsgs]
  })
  return true
}
方案二：会话历史分层存储（更工程化）
短期记忆（内存）：
  - 最近 N 条消息 → LangGraph State
  - SQLite Checkpoint（session 级别持久化）
长期记忆（数据库）：
  - 超过阈值的对话 → 存入 MySQL
  - 用户可以检索历史会话
  - 开启新会话时，检索相关历史注入 context
这个方案你后端已经有 MySQL 了，可以直接用。

方案三：RAG 风格的历史检索
不是简单摘要，而是把历史会话也向量化：
- 用户问新问题 → embedding(query)
- 在历史会话中做 similaritySearch
- 把相关历史注入到 prompt
