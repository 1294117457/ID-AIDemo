## 一、问题根因分析

### 现象
前端管理端报错 `未知错误: No static resource api/agent/knowledge/stats`。

### 全链路分析

**三层请求路径对照：**

| 调用方 | 目标 | 路径 |
|--------|------|------|
| 前端 | → 后端 | `GET /api/knowledge/stats` |
| 后端 | → idagent | `GET http://localhost:3001/knowledge/stats` |
| idagent | 监听 | `http://0.0.0.0:3001/*` |

**根本原因：后端缺少 KnowledgeController**

前端的 knowledge 接口路径是 `/api/knowledge/*`，但后端只有 `AIAgentController`（`/api/agent/*`）和 `AIConfigController`（`/api/ai-config`），没有任何 handler 处理 `/api/knowledge/*`，导致 Spring Boot 返回了 "No static resource" 错误。

**修复方案：**
1. 前端 `apiAIagent.ts` — knowledge 接口去掉 `/agent` 前缀（`/api/agent/knowledge/*` → `/api/knowledge/*`）
2. 后端新建 `KnowledgeController`（`/api/knowledge/*`），代理到 idagent `/knowledge/*`

## 四、关键数据流检查

### 4.1 知识库统计流
```
后端 getKnowledgeStats()
  → GET http://localhost:3001/api/knowledge/stats
  → knowledge.ts router.get('/stats')
    → getStats() [rag.ts]
      → listFileMeta() [store.ts]  ← 从内存 Map 读取
      → 返回 { totalFiles, totalChunks, files[] }
```

✅ RAG 重构后：元数据从 `rag_meta.json` 改为内存 Map，`getStats()` → `listFileMeta()` → Map.entries() 逻辑不变，功能完全一致。

---

### 4.2 文件上传入库流
```
后端 uploadKnowledge(file)
  → POST http://localhost:3001/api/knowledge/upload
  → knowledge.ts router.post('/upload')
    → ingestFile(buffer, fileName) [rag.ts]
      → loadFile() [loader.ts] 解析文件
      → splitAndTag() [loader.ts] 分块
      → addDocuments() [store.ts] 入库 Chroma
      → setFileMeta() [store.ts]  ← 写入内存 Map（原来是 JSON 文件）
```

✅ RAG 重构后：入库逻辑完全一致，只是元数据存储从文件改为内存 Map，行为不变。

---

### 4.3 Agent 对话流
```
后端 agentChat(message, sessionId, file, templates, userInfo)
  → POST http://localhost:3001/api/agent/chat (multipart)
  → agent.ts router.post('/chat')
    → parseAgentParams() 解析 multipart
    → invokeAgent() [service.ts]
      → getCompiledGraph() → LangGraph 图
        → classifyNode → classifyNodes.ts
        → applyGraph → applyNodes.ts
        → consultGraph → consultNodes.ts
      → 返回 { reply, intent, documentText, suggestions }
```

✅ 完整流程无变化，与重构无关。

## 五、RAG 重构影响评估

### 5.1 已简化（功能不变）

| 原逻辑 | 重构后 | 影响 |
|--------|--------|------|
| `rag_meta.json` 文件读写 | 内存 `Map` | ✅ 无影响，对外 API 不变 |
| `loadMeta()` / `saveMeta()` | `Map.set/get/delete` | ✅ 无影响，函数签名不变 |
| `resetStore()` + 事务保护 | 直接 `deleteBySource` | ✅ 无影响，外部只调 `removeSource()` |
| `_embedDimensions` 缓存 | 移除（不需要） | ✅ 无影响，Chroma 内部处理 |

### 5.2 保留的设计

| 设计 | 原因 |
|------|------|
| `sourceFile` metadata | `deleteBySource()` 需要按文件名过滤 Chroma 中的文档 |
| `FileMeta` 接口 | 内存 Map 仍用同样结构 `{ chunkCount, textLength }` |

### 5.3 注意事项

**重启后元数据丢失**：内存 Map 在服务重启后会清空，意味着：
- `init_docs/` 中的文件需要重新入库
- 用户上传的文件元数据（chunkCount）丢失
- 解决建议：后续可考虑在 `resetStore` 后由调用方重新触发入库

**现有数据兼容性**：Chroma 向量数据（`data/chroma/` 目录）不受影响，仍然持久化在磁盘。
