## 一、MCP 架构定位

### 当前结构

```
src/
├── 1config/     配置层
├── 2model/      模型工厂层
├── 3state/      状态定义层
├── 4node/       节点层
├── 5graph/      图编排层
├── 6service/    服务编排层
└── 7controller/ Controller 层
    ├── agent/
    ├── analyze/
    ├── config/
    ├── conversation/
    ├── health.ts
    └── knowledge/
src/7mcp/        MCP 工具调用层（后引入）
```

### 结论：MCP 应保持独立层

MCP 在架构中扮演的是 **Agent ↔ 后端 Java 服务** 的桥梁角色——它是工具调用层（Tool Layer），不属于业务编排（Graph/Service），也不属于 HTTP 适配（Controller）。它与 Controller 平行、同级，共同构成 Agent 的对外能力。

```
Agent 内核（1-6）
  ├── 1config   配置
  ├── 2model    模型
  ├── 3state    状态
  ├── 4node     节点
  ├── 5graph    图编排
  └── 6service  编排

对外能力（7）
  ├── 7mcp        → 调用后端 Java（工具调用）
  └── 7controller → 暴露 HTTP API（适配层）
```

保持独立层是正确的架构选择。若未来 MCP 工具增多（更多后端能力需接入），继续扩展此层即可，无需合并到 Controller 或 Service。

## 二、功能性问题

### 2.1 `analyzeCertificate` 存在两份实现（🔴 高优先级）

| 文件 | 实现位置 |
|---|---|
| `src/6service/KnowledgeService.ts` | `analyzeCertificate()`、`generateRemark()`（**被 controller 引用**） |
| `src/6service/AnalyzeService.ts` | `analyzeCertificate()`、`generateRemark()`（**无人调用，为死代码**） |

两份实现逻辑几乎相同，但各自独立维护。若业务逻辑需要同步修改，必然产生代码漂移风险。

- `analyze/index.ts` controller（line 4）调用的是 `KnowledgeService.ts` 版本
- `AnalyzeService.ts` 的版本没有任何地方 import，编译后属于死代码

**建议**：删除 `AnalyzeService.ts`，统一使用 `KnowledgeService.ts` 的实现。

---

### 2.2 `memory.ts` 中存在死代码（🟠 中优先级）

`src/4node/memory.ts` 中定义了以下函数，但从未被任何地方 import：

```typescript
export async function summarizeConversation(...)  // 未使用
export function splitMessages(...)               // 未使用
export function getCompressThreshold()           // 未使用
export function getKeepRecent()                  // 未使用
```

其中 `splitMessages` 实际上在 `compressMessages` 中被"手工等价实现"了一次（line 79-84 直接写了相同的切片逻辑），而非调用该函数。

**建议**：删除这四个未使用的导出函数。

---

### 2.3 `SKIP_NODES` 字符串硬编码（🔴 高优先级）

`src/6service/AgentService.ts`：

```typescript
const SKIP_NODES = new Set(['classify', 'ask', 'retrieve', 'fetchPolicy', 'analyzeAndMatch', 'summarize'])
```

这六个节点名与 `graph.ts` 中定义的节点名完全耦合。如果后续在 graph.ts 中重命名节点（如 `analyzeAndMatch` → `analyze`），硬编码不会产生任何编译期错误，streaming 时只会静默丢失对应节点的 token 输出，导致难以排查的 bug。

**建议**：将节点名集中到常量文件（如 `src/constants.ts`），或从 graph 导出一个节点列表常量。

---

### 2.4 `resumeAgent` 缺少 `userToken` 透传（🟡 低优先级）

`src/6service/AgentService.ts`，line 120-127：

```typescript
export async function resumeAgent(sessionId: string, supplement: string): Promise<AgentResult> {
  const config = { configurable: { thread_id: sessionId } }  // ← 缺少 userToken
  const app = await getApp()
  const result = await app.invoke(new Command({ resume: supplement }), config)
  // ...
}
```

而 `invokeAgent`、`streamAgent`、`streamResume` 的 config 中均有传递 `userToken`。`resumeAgent` 若在 resume 后触发后续 MCP 调用（如 `submitNode`），会缺少 token。

**建议**：参照 `streamResume`，为 `resumeAgent` 增加 `userId` 和 `userToken` 参数。

## 三、代码结构问题

### 3.1 `ScoreTemplate` / `TemplateRule` 类型三处定义（🟠 中优先级）

| 定义位置 | 用途 |
|---|---|
| `src/3state/state.ts` | 业务状态中的模板类型 |
| `src/7mcp/types.ts` | MCP 响应的模板类型（结构相同） |
| `src/6service/types.ts` | 引用 `3state/` 的 ScoreTemplate |

两份类型结构完全一致，但分散在两个模块维护。后续若模板结构变更，容易只改一处忘另一处。

**建议**：建立 `src/types/shared.ts`，统一导出所有跨层共用的业务类型（`ScoreTemplate`、`TemplateRule`、`UserInfo`、`McpToolResult` 等）。

---

### 3.2 `decodeFileName` 函数重复（🟠 中优先级）

完全相同的函数出现在两处：

- `src/6service/AgentService.ts`，line 241-243
- `src/6service/KnowledgeService.ts`，line 10-12

```typescript
function decodeFileName(name: string): string {
  return Buffer.from(name, 'latin1').toString('utf8')
}
```

**建议**：提取到 `src/utils.ts`，各模块按需 import。

---

### 3.3 Controller 层与 Service 层类型定义风格不统一（🟠 中优先级）

- `src/6service/types.ts`：`templates` 是 `ScoreTemplate[]`（对象数组）
- `src/7controller/types.ts`：`templates` 是 `string`（JSON 字符串化）

这种"字符串化版本"与"对象版本"并存，增加理解成本，且 JSON 解析时机不明确（controller 解析还是 service 解析）。

**建议**：Controller 层只做请求解析和响应封装，类型定义统一在 `src/types/shared.ts`，各层引用共享类型。

---

### 3.4 `prompts.ts` 放置层级不准确（🟠 中优先级）

`src/4node/prompts.ts` 被以下模块引用：

- `src/4node/consultNodes.ts`（consult 子图节点）
- `src/4node/apply/nodes/analyzeMatchNode.ts`（apply 子图节点）
- `src/4node/classifyNodes.ts`（主图节点）

它跨越了多个子图，并非专属 node 层。建议移至 `src/prompts.ts`（顶层），注释说明"所有 LLM 提示词模板集中管理"。

---

### 3.5 `rag/` 缺少数字前缀（🟠 中优先级）

其余所有层均使用数字前缀（`1config`、`2model` … `7controller`），唯独 `rag/` 是例外。它被 `4node/` 和 `6service/` 引用，属于基础设施层，建议重命名为 `8rag/` 以保持编号体系一致。

---

### 3.6 `getApp()` / `getCompiledGraph()` 双重单例（🟡 低优先级）

`AgentService.ts` 有模块级单例：

```typescript
let _app: any = null
async function getApp() { if (!_app) _app = await getCompiledGraph(); return _app }
```

而 `graph.ts` 中 `getCompiledGraph()` 内部又有一层单例：

```typescript
export async function getCompiledGraph() {
  let _compiled: any = null
  // ...
}
```

双重懒加载，异常栈会变得不清晰。

**建议**：统一为单一单例入口，仅在 `graph.ts` 保留。

## 四、健壮性与风格问题

### 4.1 `classifyPrompt` 函数末尾多余冒号（🟡 低优先级）

`src/4node/prompts.ts`，line 7：

```typescript
return `...请以 JSON 格式返回结果。：`
                                        ↑ 多余的冒号
```

---

### 4.2 JSON 解析逻辑重复出现多次（🟡 低优先级）

`checkResults` 的 JSON 解析（`map → JSON.parse → filter`）在以下函数中各自重复实现：

| 文件 | 函数 |
|---|---|
| `src/4node/apply/nodes/confirmNode.ts` | `confirmRoute()` |
| `src/4node/apply/nodes/confirmNode.ts` | `confirmNode()` |
| `src/4node/apply/nodes/summarizeNode.ts` | `summarizeNode()` |
| `src/4node/apply/nodes/submitNode.ts` | `submitNode()` |
| `src/6service/AgentService.ts` | `extractResult()` |

**建议**：在 `src/4node/apply/utils.ts` 中提取 `parseCheckResults()` 共享函数。

---

### 4.3 `mcpFetch` 的 `Content-Type` header 处理不够健壮（🟡 低优先级）

`src/7mcp/mcpClient.ts`，`GET` 请求也携带了 `Content-Type: application/json` header。虽然 HTTP 规范中这不会导致错误，但会污染日志。

**建议**：只在 `POST`/`PUT`/`PATCH` 请求中添加 `Content-Type`。

---

### 4.4 `apply/index.ts` 导入路径风格不一致（🟡 低优先级）

```typescript
export { fetchPolicyNode }     from './nodes/fetchPolicyNode.js'   // ← 从 nodes/ 目录
export { analyzeMatchNode }   from './nodes/analyzeMatchNode.js'   // 从 nodes/
export { summarizeNode }      from './nodes/summarizeNode.js'      // 从 nodes/
export { confirmRoute, confirmNode } from './nodes/confirmNode.js'  // 从 nodes/
export { submitNode }        from './nodes/submitNode.js'          // 从 nodes/
```

实际 `fetchPolicyNode` 在 `nodes/` 子目录下，其余节点也在 `nodes/` 下——此处的路径本身是正确的。但需注意 `fetchPolicyNode` 在 `graph.ts` 中被作为子图内联节点引用，路径正确不代表职责边界清晰。确认 graph.ts 中 `applySubgraph` 的节点注册顺序符合预期。

## 六、整体评价

**优点：**
- 七层架构设计思路清晰，层间职责边界明确
- State/Reducer 模式使用规范，类型安全
- 注释详尽，每个模块都有清晰的职责说明
- Config 层支持 DB 动态配置 + .env fallback，兼顾灵活性
- MCP 工具鉴权（JWT 透传）设计合理，不直连 MySQL
- RAG 模块完整（加载 → 分块 → 存储 → 检索），支持多种文件格式

**需改进：**
- 重复代码收敛不足（类型、函数、JSON 解析逻辑多处重复）
- 部分边界情况处理（如 `resumeAgent` 缺 token）有遗漏
