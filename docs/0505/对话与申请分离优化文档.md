# AI 对话/申请 分离优化文档

> 日期：2026-05-05  
> 目标：修复历史对话显示问题，将申请功能从对话中拆分出去

## 一、问题分析

### 1.1 历史对话显示问题

API 请求已成功（返回 `code: 200`，共 3 条记录），但前端显示不正确，根因如下：

**后端：`AiConversationProxyController.java` 第 193-198 行**

```java
@GetMapping("/list")
public ResultVo listConversations(...) {
    ...
    ForwardResult r = forwardGet("/ai/conversation/list?limit=...", uid);
    if (r.bodyCode == 200) return ok(r.data);   // ← 直接返回 r.data
    return fail(r.bodyCode, r.bodyMsg);
}
```

idagent 返回的结构是：

```json
{ "code": 200, "msg": "成功", "data": { "list": [...], "total": 3 } }
```

proxy 将 `r.data`（即 `{ "list": [...], "total": 3 }`）原封不动放到 ResultVo.data 中返回，前端收到的结构完全正确。

**真正问题在前端：`idfrontend/src/views/ai-agent/index.vue` 第 677-681 行**

```typescript
const res = keyword
  ? await searchConversationsApi(keyword)
  : await getConversationsApi()
// ↓ 搜索结果直接赋值 list，但列表结果却用了 data.list
conversations.value = keyword
  ? (res.data as ConversationMeta[])                          // ✅ 搜索
  : (res.data as { list: ConversationMeta[] }).list          // ⚠️ 列表
```

这个逻辑本身是对的。**真正的问题在于**：`displayConversations` 和 `groupedConversations` 的分组逻辑完全依赖 `updated_at` 字段：

```typescript
const date = conv.updated_at.slice(0, 10)   // 取 '2026-05-05'
```

所有会话的 `updated_at` 都恰好是今天（`2026-05-05T08:39:12.039Z` 等），所以它们确实只显示在一个日期分组下，这是**正常行为**，但如果用户感觉显示不对，可能是以下原因之一：

1. **`last_message` 全为 `null`**：后端 `ConversationService` 的 `getConversations` 在查询时可能没有正确更新或返回 `last_message` 字段。
2. **分组后每个分组只有一个会话**，视觉上看起来"只有一条"。
3. **搜索模式 `keyword` 有值但为空字符串**，导致走错分支。

**需要确认**：`ConversationService.ts` 中 `getConversations` 的 SQL 是否正确 JOIN 或 SELECT 了 `last_message` 字段。历史记录显示"新对话"而非真正的最后一条消息，说明 `last_message` 确实为空。

### 1.2 对话 vs 申请 混淆问题

当前 LangGraph 图架构如下：

```
START → classify
           ├─ intent=consult → consultGraph → retrieve → answer → END
           ├─ intent=apply   → applyGraph   → fetchPolicy → analyze → summarize → [interrupt 等待前端] → confirm → submit → END
           └─ intent=insufficient → ask (要求补充信息)
```

问题：AI 在 `consultGraph`（纯对话咨询）中也可能主动触发 `apply` intent，用户在对话过程中可能被"引导"进入申请流程，这与需求不符。

**需要实现**：对话（consult）保持纯对话，不主动引导用户进入申请；申请（apply）功能仅通过独立入口触发。

## 二、修复计划

### 阶段一：修复历史对话 last_message 为空（高优先级）

**涉及文件**：`idagent/src/6service/ConversationService.ts`

**现状**：`getConversations` SQL 可能只查询了会话表，没有正确 JOIN 或 SELECT 最新消息的 content 作为 `last_message`。

**目标**：返回每个会话的 `last_message` = 该会话最新一条消息的内容（content），按 `updated_at` 降序排列。

**参考表结构**（推测）：

```sql
CREATE TABLE conversations (
    id INTEGER PRIMARY KEY,
    user_id TEXT,
    session_id TEXT UNIQUE,
    title TEXT DEFAULT '新对话',
    status INTEGER DEFAULT 1,
    is_deleted INTEGER DEFAULT 0,
    created_at TEXT,
    updated_at TEXT,
    message_count INTEGER DEFAULT 0,
    last_message TEXT  -- 这个字段目前为空
);

CREATE TABLE messages (
    id INTEGER PRIMARY KEY,
    session_id TEXT,
    role TEXT,
    content TEXT,
    msg_type TEXT,
    extra_data TEXT,
    created_at TEXT,
    FOREIGN KEY (session_id) REFERENCES conversations(session_id)
);
```

**修复方案**：在 `getConversations` 中，对每个会话通过子查询获取 `messages` 表中该会话的最新一条 `content` 作为 `last_message`。

```sql
SELECT c.*,
  (SELECT content FROM messages WHERE session_id = c.session_id
   ORDER BY created_at DESC LIMIT 1) AS last_message
FROM conversations c
WHERE c.user_id = ? AND c.is_deleted = 0
ORDER BY c.updated_at DESC
LIMIT ? OFFSET ?
```

### 阶段二：对话/申请功能分离（核心改造）

#### 2.1 前端：两套独立入口

| 入口 | 组件 | 路由 | 功能 |
|------|------|------|------|
| AI 对话 | `idfrontend/src/views/ai-agent/index.vue` | 已存在（悬浮按钮） | 纯对话咨询，不涉及申请 |
| 申请助手 | 新建 `idfrontend/src/views/ai-apply/index.vue` | `/ai-apply` | 申请加分引导 + 证明材料上传 + 提交 |

**idfrontend 改造点**：

1. `src/views/ai-agent/index.vue` — 保持现有对话逻辑不变，但 **移除** `interrupt` 中包含的申请引导信息（applyGraph 触发的 interrupt 对话框不再引导用户去申请）。
2. `src/views/ai-apply/index.vue`（新建）— 独立的申请页面，流程：
   - 用户输入/上传材料 → 调用 `/api/ai/agent/stream`（强制 `intent=apply` 模式）
   - agent 返回 `interrupt`（含 suggestions）→ 前端显示加分匹配结果卡片
   - 用户点击"确认提交" → 上传证明材料 → 调用 `confirm` API → agent 进入 `submitNode` → 提交给 Java 后端
3. `src/router/index.ts` — 添加 `/ai-apply` 路由，指向新页面。
4. **顶部导航或首页**添加"申请助手"入口按钮，引导用户进入申请流程。

#### 2.2 后端 idbackend：新增申请代理 Controller（可选复用）

如果申请页面需要直接调用 agent，可以：

- 方案 A（推荐，复用现有）：前端申请页面继续调用 `/api/ai/agent/stream`，idbackend 透传，无需新增 Controller。
- 方案 B：新增专用 `/api/ai/apply/*` Controller，在后端层面直接指定 `intent=apply`。

#### 2.3 idagent：新增申请专用 API

**文件**：`idagent/src/7controller/apply/index.ts`（新建）

新建一个专门用于申请流程的路由：

```
POST /ai/apply/start    — 强制进入 applyGraph，跳过 classify
POST /ai/apply/confirm — 用户确认加分项 + 上传材料后提交
```

或者更简单的方案：前端在调用 `/ai/agent/stream` 时，通过 `body.intent = 'apply'` 参数强制指定 intent，agent 不走 classify 节点，直接进入 applyGraph。

需要在 `AgentService.ts` 的 `parseAgentParams` 中支持 `intent` 参数，并在 `streamAgent` 中如果指定了 intent 则跳过 classify。

#### 2.4 LangGraph 图：可选优化

**可选优化**（非必须）：将 `classifyNode` 改为可配置模式——如果传入参数指定了 intent，则直接用指定 intent，不执行分类。

```typescript
// 改造 classifyNode 支持强制 intent
export function classifyNode(state: MainState): Partial<MainState> {
  if (state.forcedIntent) {           // ← 新增字段
    return { intent: state.forcedIntent }
  }
  // 原有的 LLM 分类逻辑
  ...
}
```

## 五、注意事项

1. **不破坏现有对话功能**：悬浮按钮的对话入口保持不变，`ai-agent/index.vue` 改动应最小化。
2. **申请流程的 interrupt 交互**：目前 `applyGraph` 的 `interrupt` 通过前端 `interrupt` 消息气泡的"提交"按钮触发，新申请页面需要复用这套机制。
3. **证明材料上传**：需要额外实现文件上传逻辑（参考 `rag/upload.ts` 的 `/rag/upload` 接口）。
4. **session 复用**：申请流程和对话流程使用同一个 `sessionId` 体系，可以共用会话列表 API，但申请会话和咨询会话在 `title` 或 `status` 上应有区分（如 `status=2` 表示申请会话）。
