## 问题一：删除会话报错"删除失败"，但 HTTP 状态码为 200

### 现象

- 点击删除按钮，发送 `DELETE /api/ai/conversation/sess_xxx`
- HTTP 响应状态码：**200 OK**
- 浏览器控制台显示：**"删除失败"**（前端 ElMessage.error）

### 根因分析

完整数据链路：

```
前端 deleteConversationApi(sess_xxx)
  → apiClient.delete(...)
  → idbackend /api/ai/conversation/{sessionId} DELETE
    → idagent /ai/conversation/{sessionId} DELETE
      → idbackend 返回 { code: 200, msg: '成功', data: null }
    → apiClient 响应拦截器检查 res.code === 200 → 通过
    → 返回 res (即 { code: 200, msg: '成功', data: null })
  → 前端 await 拿到 { code: 200, msg: '成功', data: null }
```

**理论上 `res.code === 200` 应该通过，删除应该成功。** 但根据之前的调试日志，`getConversationsApi` 返回的是 `{ total, list }`（无 `code` 字段），说明 idbackend 到前端之间存在**响应格式不一致**的问题。

可能原因：
1. idbackend 的某些 Controller 在返回前做了响应体替换（不经过 `ResultVo` 统一包装）
2. 某些请求路径（如 DELETE）走了不同的拦截器链路

**真正的问题**：即使删除操作在 HTTP 层面成功，前端的 `handleDeleteConversation` 依赖 `res.code === 200` 判断，而 `res.code` 可能为 `undefined`，导致走入了 catch 分支。

### 修复方案（任选其一）

#### 方案 A：前端防御性修改（推荐，改动最小）

**文件**：`idfrontend/src/views/ai-agent/index.vue` 第 744-758 行

```typescript
// 删除会话
const handleDeleteConversation = async (conv: ConversationMeta) => {
  try {
    const res = await deleteConversationApi(conv.session_id)
    // 兼容两种响应格式：无 code 字段时只要没抛异常就视为成功
    const success = res && (res.code === 200 || res.code === undefined)
    if (success) {
      conversations.value = conversations.value.filter(c => c.session_id !== conv.session_id)
      ElMessage.success('删除成功')
      if (currentSessionId.value === conv.session_id) {
        await handleNewConversation()
      }
    } else {
      ElMessage.error((res as any).msg || '删除失败')
    }
  } catch (e) {
    ElMessage.error('删除失败')
    console.error(e)
  }
}
```

## 问题二：点击历史会话，消息列表为空

### 现象

- 点击历史会话列表中的某一项
- 发送请求 `GET /api/ai/conversation/{sessionId}/messages`
- 返回：`{"code":200,"msg":"成功","data":[]}`
- 消息列表为空，没有历史对话内容

### 根因分析

**核心结论：消息根本没有被持久化到 SQLite 数据库。**

数据流追踪：

```
用户发送消息
  → 前端 handleSend()
  → agentStreamChat() 发送 SSE 请求到 idagent
  → idagent AgentService.stream() 接收流式响应
  → 流式 token 通过 SSE 推送给前端
  → 流结束 → 写入数据库 ← 【关键缺失步骤】
```

查看 `idagent/src/6service/AgentService.ts`：

```typescript
// stream() 函数中的消息保存逻辑
// 第 131 行：用户消息
appendMessage(sessionId, 'user', message)  // ← 写入了

// 第 160 行：助手消息
appendMessage(sessionId, 'assistant', fullContent)  // ← 流结束后写入
```

**但问题是**：`stream()` 函数的 `finally` 块（第 186 行）中，消息保存代码的逻辑分支可能存在问题。查看代码第 183-191 行：

```typescript
} finally {
  // 如果之前没有写入过 assistant 消息（流中断等异常情况），这里补写
  if (!assistantWritten.get(sessionId)) {
    assistantWritten.set(sessionId, true)
    if (fullContent.trim()) {
      appendMessage(sessionId, 'assistant', fullContent)  // 条件：fullContent.trim() 非空
    }
  }
}
```

可能的原因：
1. **LangGraph 内部保存了对话，但没有更新 `fullContent`** — 流式 token 通过 `onToken` 回调累积，但如果 `onToken` 在某个分支提前返回，`fullContent` 可能为空或不完整
2. **`interrupt` 消息写入问题** — interrupt 消息只在特定分支写入，如果流程没有进入该分支，interrupt 消息不会保存
3. **新增会话时的竞态条件** — `appendMessage` 在 `streamEvents` 之前调用，但如果会话刚创建而数据库事务尚未提交，后面的查询可能查不到

### 修复方案

需要确认 `stream()` 函数中消息持久化的具体逻辑，排查 `fullContent` 是否正确累积。

建议在 `AgentService.ts` 中增加日志，确认 `appendMessage` 被调用：

**文件**：`idagent/src/6service/AgentService.ts` 第 198-208 行附近

在 `appendMessage` 调用后增加日志：

```typescript
appendMessage(sessionId, 'user', message)
console.log(`[DEBUG] Saved user message for session ${sessionId}, content length: ${message.length}`)

try {
  // ... streaming loop ...

  // 在 finally 块中
  finally {
    if (!assistantWritten.get(sessionId)) {
      assistantWritten.set(sessionId, true)
      if (fullContent.trim()) {
        appendMessage(sessionId, 'assistant', fullContent)
        console.log(`[DEBUG] Saved assistant message for session ${sessionId}, content length: ${fullContent.length}`)
      } else {
        console.warn(`[DEBUG] assistant content empty for session ${sessionId}, skipping save`)
      }
    }
  }
}
```

然后重新发起一次对话，查看 idagent 控制台日志，确认：
1. 用户消息是否写入 → 预期：`Saved user message for session sess_xxx`
2. 助手消息是否写入 → 预期：`Saved assistant message for session sess_xxx, content length: N`
3. 如果显示 `content length: 0` 或 `skipping save`，则说明流式 token 累积失败

**根据日志结果决定下一步修复方向**。

## 总结：两个问题的共同根因

| 问题 | 根因 | 修复方式 |
|------|------|----------|
| 删除失败 | 前端 `res.code === 200` 判断在响应无 `code` 字段时失效 | 前端做响应格式兼容性处理（方案 A 最快） |
| 消息为空 | 消息未持久化到 SQLite（或持久化失败但无日志） | 在 AgentService 中加日志排查，确认 `appendMessage` 是否被调用 |

两个问题都指向**同一类根因**：响应/数据格式不一致 + 缺少日志导致问题难以追踪。建议优先在 `AgentService.ts` 加调试日志，重现实验对话后确认消息写入情况。
